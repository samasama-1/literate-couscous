# Collection hardening review and revised implementation plan

Current follow-up: the pickup-code draft has been replaced locally by [named collector + photo-ID handover](named-collector-rollout.md). Its one-use owner link, role/retention guards and regression tests supersede the old pickup-code recommendations below. Other storage, notice, privacy and deployment blockers remain. The original vulnerable-behavior diagnostic was retired; use `tests/collection-named.test.mjs` for the replacement regression coverage. This is not production activation.

Date: 26 October 2026. Decision: **hold deployment of the collection/storage draft until the mandatory corrections below are completed and accepted.**

This reviews the local, uncommitted 26 October implementation, not a verified production deployment. No application logic or commercial terms were changed during this review. Only this report, a cross-reference in the earlier rollout guide, and a synthetic diagnostic script were added. No remote SQL, deployment, production setting, customer email or Google Sheet was changed.

Risk ratings describe the current draft: High = potential unauthorised release, materially incorrect billing or credential disclosure; Medium = material defence/operational/reconciliation weakness with additional prerequisites. No anonymous remote-code-execution or unauthenticated direct-table access was identified in this scoped review. That is not a whole-site security certification.

**M** means mandatory before launching the affected capability. A capability can remain explicitly disabled instead; existing payment/owner-handover safeguards must remain enabled. **O** means optional improvement, subject to the conditions stated. Proposed security timeouts, reminder schedules and retention windows are recommendations, not settings already applied or commercial decisions already approved.

## 1. Pickup-code security — Medium, M before delegated collection

Affected: [src/app/actions/collections.ts:19](/Users/marcus/AntiGravity/group-buy-app/src/app/actions/collections.ts:19), [src/app/actions/order-operations.ts:27](/Users/marcus/AntiGravity/group-buy-app/src/app/actions/order-operations.ts:27), [src/lib/collections/access.ts](/Users/marcus/AntiGravity/group-buy-app/src/lib/collections/access.ts), [database/sql/collection_management.sql:110–143](/Users/marcus/AntiGravity/group-buy-app/database/sql/collection_management.sql:110), [tests/collections.test.mjs](/Users/marcus/AntiGravity/group-buy-app/tests/collections.test.mjs).

Current codes have 90 million possible values: the generator excludes leading zero. Plain SHA-256 permits inexpensive offline guessing if code hashes are exposed. RLS/service-only RPCs currently prevent an anonymous online guessing endpoint, but admin verification has no distributed attempt budget or failed-attempt monitoring. The 8-per-10-minute limit applies to *creating/changing authorisations*, not verifying pickup codes. Twenty wrong codes followed by a correct code succeeded locally, without a lockout or failed-attempt audit.

Recommended correction:

- Store a keyed MAC such as HMAC-SHA-256 over a versioned, unambiguous encoding of purpose + order ID + authorisation ID + code. Generate the authorisation ID before computing the MAC. Use an independent server-only pickup key and key ID; do not rotate `ORDER_EMAIL_LINK_KEY` casually, because that would also break existing encrypted balance jobs/links. HMAC protects against a code-table-only compromise, not a compromised application/service-role credential.
- Do not accept a MAC from the browser. The authenticated server action computes it; SQL verifies the matching current authorisation and MAC. Use constant-time comparisons in application-side secret comparisons. Keep plaintext codes out of logs, analytics, audit rows, exports and notification jobs.
- Enforce a durable, indexed verification budget across all instances and all application fulfilment entry points. Proposed starting point: five failed attempts per authorisation per 15 minutes, with an additional staff/session budget and alert threshold; tune in tests. On exhaustion, require a fresh owner-verified reissue or an audited management recovery, not an unlimited clerk retry.
- A failed verification must **commit** the failure counter. Updating a counter and then raising a SQL exception in the same transaction rolls it back. Use a guarded verifier returning a structured denied/locked status with committed counters, or a separate committed limiter call before handover; recheck authorisation/state and consume the code atomically at handover. Fail closed if the limiter is unavailable. Do not return a reusable “verified” flag to the browser that bypasses the final check.
- Log only safe event labels, an internal/pseudonymous authorisation reference, staff identity and count/time. Alert on repeated failures, cross-order attempts and suspicious reissue/revoke bursts; name the person responsible for reviewing alerts. Do not turn attacker-triggered lockout into an owner-inaccessible permanent hold.
- Migration must version MAC records. Old SHA hashes cannot be converted without the code. If any such records exist in the target environment, revoke/reissue them through verified owners rather than silently maintaining an indefinite SHA fallback.

O: longer/QR-based random collection credentials can supplement the human-entered code; they do not replace attempt controls or one-time consumption.

## 2. Delegated-collection management — High, M before delegated collection

Affected: [src/lib/collections/access.ts:5–18](/Users/marcus/AntiGravity/group-buy-app/src/lib/collections/access.ts:5), [src/lib/collections/server.ts](/Users/marcus/AntiGravity/group-buy-app/src/lib/collections/server.ts), [src/app/actions/collections.ts](/Users/marcus/AntiGravity/group-buy-app/src/app/actions/collections.ts), [src/app/collection/[token]/page.tsx](/Users/marcus/AntiGravity/group-buy-app/src/app/collection/[token]/page.tsx), [src/components/CollectionAuthorisationForm.tsx](/Users/marcus/AntiGravity/group-buy-app/src/components/CollectionAuthorisationForm.tsx), [src/lib/order-integrations/worker.ts:36–44](/Users/marcus/AntiGravity/group-buy-app/src/lib/order-integrations/worker.ts:36), [src/lib/order-integrations/messages.ts](/Users/marcus/AntiGravity/group-buy-app/src/lib/order-integrations/messages.ts), [database/sql/order_integrations.sql](/Users/marcus/AntiGravity/group-buy-app/database/sql/order_integrations.sql), collection SQL.

A reusable 30-day bearer link currently reads collection details and can create, replace or revoke collectors with no fresh owner verification or change notification. A forwarded email or leaked URL grants that authority. Knowing the order owner's name, email or phone is not fresh identity verification; do not reuse the low-disclosure order-lookup check for these mutations. Link claims also expose an unkeyed email hash in base64url data; it is not encryption and can be tested against candidate email addresses.

Recommended correction:

- Replace the long-lived action-bearing URL with a short-lived entry/recovery mechanism; proposed initial validity 24 hours. Exchange it only after an explicit owner action, not a GET that an email scanner could consume. Store a server-side, revocable, opaque session with a Secure/HttpOnly/SameSite cookie rather than carrying long-lived authority in the URL or localStorage. Avoid putting an email hash in URL claims.
- Require a fresh single-use OTP or equivalent verified-owner challenge for **every create/replace/revoke collector mutation**. Proposed challenge validity ten minutes; bind to order, authorisation revision, action and intended new collector, and consume atomically with the mutation. Deliver only to the existing verified owner contact, never an address supplied by the person attempting the change. Apply separate issuance and verification limits and generic anti-enumeration responses. Support recovery needs an approved owner-verification procedure.
- A transaction creates/replaces/revokes the authorisation, invalidates old codes/grants, and creates a unique owner-notification outbox event. Notifications go to the trusted owner contact; contact changes should notify the prior trusted contact too where appropriate. A notification never includes the pickup code or a new management credential, and need not disclose the full collector phone number.
- Queue these security notifications separately/prioritise them so a blocked earlier order-confirmation job cannot hide an authorisation change. Alert on notification failure. Do not claim guaranteed exactly-once email delivery: retain the existing uncertain-send reconciliation rule and deduplicate on order + authorisation revision + event.
- Enforce grant expiry and revision again **inside SQL after acquiring the order lock**. The present token expiry is only checked before the application makes database requests.

O: authenticated customer accounts/passkeys can replace repeated email challenges later. They are not required to implement a secure initial step-up flow. The short-link/challenge lifetimes above need usability review and do not change the customer's collection deadline.

## 3. Email-dependent storage fees — High, M before charging storage

Affected: [database/sql/collection_management.sql:27–65](/Users/marcus/AntiGravity/group-buy-app/database/sql/collection_management.sql:27), [src/lib/order-integrations/worker.ts:22–24,55–62](/Users/marcus/AntiGravity/group-buy-app/src/lib/order-integrations/worker.ts:22), [src/lib/mail/zoho-transport.ts](/Users/marcus/AntiGravity/group-buy-app/src/lib/mail/zoho-transport.ts), [database/sql/order_integrations.sql](/Users/marcus/AntiGravity/group-buy-app/database/sql/order_integrations.sql), collection policy copy, admin collection controls, new notification-evidence/reminder components.

Current provider `sent`/accepted status starts the storage clock. There is no delivered/bounced/deferred/disputed evidence model, bounce handler, reminder scheduler or automatic suspension. A local test confirmed that acceptance alone starts fees. The ready email also tells the owner to reply to arrange location/time: it does not prove a usable collection location/appointment is available.

Recommended correction:

- Separate transport state (queued/accepted/deferred/bounced/uncertain) from the **management-approved effective notice** and billing clock. Store immutable evidence: notice revision, contact used, provider message ID, actual collection availability/instructions, event timestamps, verified acknowledgement or approved alternative contact, suspension reason and actor.
- Initially keep fee charging off unless a valid notice/availability rule is met. While delivery evidence is unavailable, use an audited manual confirmation/owner acknowledgement workflow or leave charging off; do not infer delivery from API acceptance, a tracking-pixel open, or an email-scanner click.
- Confirmed hard bounce/non-delivery must suspend charging and create an operations task. Deferred/uncertain delivery is held pending resolution. Correct any charges for the affected notice period through an auditable adjustment; a pause starting only when a late bounce arrives does not undo earlier incorrect charges. Prevent replayed/out-of-order events from resuming a failed notice. Resume only after an approved new notice/verified alternative, with the restart/free-period treatment explicitly approved by management.
- First establish what the actual Singapore **Zoho Mail** account supports. The current transport only requests message creation/account read. Zoho Mail's incoming-message webhook documentation is not proof of a signed delivery-event webhook; the separate Zoho Email API/Campaigns bounce API must not be assumed available for this mailbox. If supported, authenticate event callbacks, validate recipient/message/revision, deduplicate and reject replays. Otherwise monitor the official sender mailbox/provider delivery records with an audited manual process. Do not trust arbitrary inbound bounce-looking messages as financial evidence.
- Retry known pre-send/definitive failures with bounded backoff. Preserve provider-outcome-uncertain quarantine; reconcile by provider ID before creating a replacement attempt. Never reset deadlines on an automatic retry. A corrected/replacement notice needs its own revision and an explicit supersession rule.
- Proposed reminders: retain the previously agreed day-3 uncollected reminder, add one 24 hours before the effective free deadline, and a warning 48 hours before the 21-day review point. These new timings/text are proposals for approval. Recompute on pause/extension/new notice; check relevance immediately before send; suppress after collection, refund/cancellation, notification dispute or suspension. A missed required warning must raise a task and hold any dependent escalation. The mechanism to issue required notices and detect failures is M; extra reminder frequency/channel is O.

References: [Zoho Mail webhooks](https://www.zoho.com/mail/help/dev-platform/webhook.html), [Zoho Mail messages API](https://www.zoho.com/mail/help/api/email-api.html), [separate Zoho Email API bounce events](https://www.zoho.com/campaigns/help/emailapi/events/bounce.html). These establish the product distinction, not verified entitlement or configuration of the production account.

## 4. Actual payment before handover — High operational risk, M

Affected: [src/app/actions/order-operations.ts](/Users/marcus/AntiGravity/group-buy-app/src/app/actions/order-operations.ts), [src/components/OrderOperationForm.tsx](/Users/marcus/AntiGravity/group-buy-app/src/components/OrderOperationForm.tsx), [src/components/CollectionCheckoff.tsx](/Users/marcus/AntiGravity/group-buy-app/src/components/CollectionCheckoff.tsx), [src/app/admin/orders/[id]/page.tsx](/Users/marcus/AntiGravity/group-buy-app/src/app/admin/orders/[id]/page.tsx), [database/sql/order_fulfilment.sql:67–113](/Users/marcus/AntiGravity/group-buy-app/database/sql/order_fulfilment.sql:67), [database/sql/collection_management.sql:96–101,127–149](/Users/marcus/AntiGravity/group-buy-app/database/sql/collection_management.sql:96), collection payment ledger.

The positive control is real: the guarded path requires verified deposit, consistent final total, verified positive balance, ready state and settled/reduced storage before release; it blocks refunded orders and repeated handover. Tests cover those gates. However, verification is **a staff assertion**, not a bank-confirmation integration. An exact amount and a unique typed reference cannot prove funds arrived. Screenshots/customer payment-success screens are not authoritative bank receipts. The same broad admin permission can change the final total, assert payment and waive storage; lowering a final total to the deposit can remove the remaining-balance gate.

Mandatory operating/implementation changes:

1. Staff consult the actual official bank/provider ledger and match recipient/payee account, settled amount, currency, bank transaction ID and relevant order. Do not release on pending transfer or customer screenshot alone.
2. Persist a reconciled receipt record with amount, source, immutable transaction ID, verified-by/time and order allocation. Use one canonical reference namespace across deposits, balance and storage. Record partial/combined/overpayments explicitly rather than inventing multiple references or treating a typed string as bank evidence. Existing cross-ledger checks are worth preserving.
3. Final-price overrides, fee waivers and refunds require the approved authority and a recorded reason. Do not silently allow a pricing shortcut to substitute for payment. Define whether one manager can both verify and release; fine-grained roles/dual approval can follow the management risk decision, but the verification procedure and approved override authority are required.
4. Handover must recheck settled allocations, latest agreed total, refund/dispute/chargeback/hold status, storage clearance and current authorisation under a row lock; a UI checkbox is not an authority. Mark handover/code used together and only then physically release the whole order. On timeout, refresh the authoritative order instead of repeating the physical handover.
5. Currently there is **no distinct pay-at-the-counter workflow**: orders cannot be marked ready until product payment is verified. For collection-day payment, staff must verify receipt first, then mark ready and perform guarded handover. If invitations to unpaid orders are required, introduce a separate inventory-ready/invitation state; do not weaken the release-paid guard. Agree this workflow before changing states or starting notice-based fees.

O: automatic bank/payment-provider reconciliation reduces manual error. A documented, tested official-bank verification workflow can be the initial launch control; automated bank access is not falsely claimed to exist.

## 6. Independent feature controls and rollback — High, M

Affected: [src/app/actions/order-operations.ts:24–27](/Users/marcus/AntiGravity/group-buy-app/src/app/actions/order-operations.ts:24), [src/lib/collections/server.ts](/Users/marcus/AntiGravity/group-buy-app/src/lib/collections/server.ts), [src/app/actions/collections.ts](/Users/marcus/AntiGravity/group-buy-app/src/app/actions/collections.ts), [src/lib/order-integrations/worker.ts](/Users/marcus/AntiGravity/group-buy-app/src/lib/order-integrations/worker.ts), admin pages, [src/lib/policies.ts](/Users/marcus/AntiGravity/group-buy-app/src/lib/policies.ts), collection SQL.

One `FULFILMENT_V2_ENABLED` flag currently controls acceptance, fees UI and delegated collection. Turning it off sends fulfilment back to the legacy RPC, removes the new management UI, and does not suspend database fee accrual. Local diagnostics confirmed the legacy privileged RPC accepts a recipient without checking the delegated code. This is a real rollback-path bypass, **not** an anonymously callable RPC exploit.

Recommended control plane:

| Control | Proposed effect | Safeguards that remain on |
| --- | --- | --- |
| Storage accrual mode: off / active / suspended | Off creates no new charge obligation; suspension records an effective pause interval for existing accepted orders; resumption does not catch up the suspended period | Existing balances/receipts/audit remain; already accrued obligations remain subject to explicit management disposition |
| Delegated collection enabled | False rejects create/replace and delegated redemption in app **and SQL** | Owner collection remains guarded; owners/admins can still revoke compromised authorisations |
| Handover enabled | Emergency false blocks all physical-release transactions | Payment recording, safe status reads, support and auditing remain available |
| Notice/reminder dispatch enabled | Stops future dispatch; identifies/reconciles in-flight sends | Notice-evidence/fee holds and uncertain-send protection remain |

- Store authoritative, audited runtime controls/effective intervals in service-only database state, not only per-deployment environment variables. Missing/unreadable controls fail closed. An environment switch can additionally disable UI, but must not re-enable charging or bypass SQL on an older build.
- Preserve a single always-guarded handover entry point. Refactor the legacy core to an owner-only internal helper or reject direct legacy fulfil calls after migration; update every server caller. Do not rely on a browser field or a freely settable SQL session flag as proof that checks occurred.
- A global suspension must cover orders notified during the suspension and clip each order's paused interval to its actual notice/stop/fulfilment timeline. Resumption must not resurrect charges for the suspended time. Do not bulk-loop a whole customer table on every request.
- Keep read/adjust/revoke facilities available when new issuance/accrual is disabled. Versioned published terms remain accessible regardless of the current operational switch; static policy pages need a deliberate rebuild when publishing terms, not when merely suspending a feature.
- Rollback: suspend accrual and delegated redemption first, account for in-flight requests, preserve receipts/accepted policies, then use a compatible code rollback/forward fix. Do not drop tables/triggers, delete fees, or switch to an unguarded RPC. Define the control transaction as the cutover point and test concurrent handovers against it.

## 8. Privacy, log redaction and retention — High for bearer-link leakage; Medium for excessive retention, M evidence/retention plan

These controls **do not redact** URLs at Cloudflare/Vercel, Supabase diagnostics, log drains, browser history, mailbox retention or monitoring vendors. No production log/configuration inspection occurred, so end-to-end redaction is **unverified**, not passed.

Required release evidence:

- Inventory actual Cloudflare/Vercel access, runtime, WAF/security, analytics and error/session-replay logs; all log drains and support screenshots; Supabase/PostgREST RPC logging; Zoho sent mailbox and forwarding; Google Apps Script exceptions. Record owner, access, retention and configuration evidence for each, without copying live secrets into the report.

Retention proposal **requires management approval**: invalidate pickup MAC/challenge secrets immediately on use/revocation/expiry; remove consumed/revoked credentials in the mutation transaction and expired credentials in the next bounded cleanup run within an approved SLA (retain only minimal event evidence); purge collector name/phone after the agreed operational/dispute period. Failed/review outbox jobs and receipts need their own approved retention schedules.

Implement an owner-only scheduled cleanup with expiry indexes, bounded batches, a short lock/statement budget, legal-hold checks, idempotence and aggregate monitoring. No public cleanup RPC. Separate ephemeral credentials/contact data from immutable financial audit so cleanup cannot cascade-delete receipts. Verify backup/PITR and mailbox/Sheets historical-copy expiry; a deletion from one live table is not instant erasure from all backups. No deletion or schedule activation is authorised by this review.

[OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) supports excluding tokens/unnecessary personal data while retaining safe security events.

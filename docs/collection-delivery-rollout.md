## What is prepared

- Delivery is labelled “subject to availability and confirmation; additional charges apply” on the checkout option. A selected-delivery explanation makes clear it is a request, not a booking. Rates and availability remain manually quoted and agreed; no delivery charge is silently added.
- Order emails, including balance requests, include the catalog product image when it is a valid HTTPS/public URL, product name, quantity, batch and order details, plus hello@samasama.sg. The private balance page has the image and support link too. Missing/blocked images leave complete text instructions. Existing payment-link encryption and queue retry/uncertain-send behavior remain in place.
- A new server-only flag, `FULFILMENT_V2_ENABLED=true`, enables versioned policy acceptance, storage controls and delegated collection together. It is not enabled by these code changes.
- Seven days free self-collection, then S$10 **per order per commenced seven-day period**, no cap. This per-order unit is the implementation assumption; confirm it before activation if you intended per item instead. Seven days means 168 hours, with deadlines displayed in Singapore time. Exact seven-day boundary is free; immediately afterwards S$10. At exactly 14 days it is S$10; immediately afterwards S$20.
- More than 21 elapsed days makes an order eligible for manual cancellation/resale review. An approved pause/extension shifts the effective deadlines. Review does not automatically cancel, refund, forfeit payments, resell or stop storage accrual. All those decisions need a documented operational process. There is no automatic disposal job.
- Admins can extend free days, pause/resume the clock, reduce/waive current outstanding charges, verify a separate storage payment, record review, stop future storage after an agreed cancellation, and revoke collection access. Every action requires a reason and is audited. Rescheduling alone has no fee effect. A reduction does not waive future weeks; use pause/extension where agreed. Stop is terminal for future accrual in this UI; it does not change payment status or cancel/refund the order.
- Owners use a one-use, 24-hour private form link from the collection-ready email to authorise a collector by full photo-ID name. The collector brings original photo ID and order code; no collector phone or pickup code is requested. Staff record the ID check, payment/storage clearance and single handover. Replacement/revocation require a fresh owner link; admins can email it to the order owner. See the replacement guide for SQL and controls.

## Existing orders and notice timing

`register_batch_order_v2` atomically creates the order and acceptance record for `collection-2026-10-v1`. The unchecked checkout consent must be given; server and SQL both enforce it. No acceptance or charge is backfilled onto existing orders. Delivery orders have no self-collection storage charge. Existing orders can still use delegated collection once enabled but keep their prior fee terms. New acceptance rows capture version and server timestamp; any materially changed future policy needs a new version and preserved historical copy.

The storage clock starts only when the ready email job is persisted as accepted by the email provider. Marking an order ready or merely queuing it does not start fees. Provider acceptance is not proof of inbox delivery: support must investigate reported non-receipt/bounces and pause, extend or reduce charges as appropriate. No bounce processing is added here. A pause requires an existing notice; do not mark ready/send a notice until collection is actually available. Pauses cover SamaSama delays and approved holds, and adjust the timeline rather than capping fees. A refund transition stops future accrual automatically. Existing accrued fees/payment history are retained for reconciliation.

Fee calculation is on demand by primary-key order lookup. No additional cron job, table scan or fee-accrual writes are scheduled. A handover trigger also protects against releasing an order with outstanding fees through the older payment RPC. Refunds, credit balances caused by later extensions/waivers, and cancellations need manual reconciliation; no money is transferred automatically.

## Security and privacy

- Every admin mutation checks the existing signed-in admin allowlist first. New tables have RLS and no anon/authenticated/Public access; new functions are owned by postgres with `search_path=pg_catalog,pg_temp`, qualified table references and service-role-only EXECUTE. No service key or signing secret enters client code.
- The new owner form link is purpose-bound, signed, state-bound and valid for 24 hours. Its version is consumed transactionally on authorise/replace/revoke. An order code alone cannot create an authorisation. Legacy pickup-code links/RPCs are retired.
- Private pages use no-store, no-referrer, noindex/nofollow and frame-denial headers and hide public site navigation. No private data is passed into marketing analytics. URLs still transit hosting/email infrastructure: redact `/collection/*` and `/balance/*` from any custom request/error analytics and limit infrastructure log access/retention.
- Existing indexed request throttling is reused for valid-link reads and mutations (40 reads/10 minutes and 8 authorisation changes/10 minutes per order). Invalid MACs make no DB calls. Changing collector records requires consent; SQL checks contact shape too. Codes never appear in audit metadata or job payloads. Rows/hashed codes and authorisation timestamps remain service-only; only operational admins see collector phone details.
- Existing payment and new storage references share the same advisory-lock namespace and cross-ledger reuse checks. Monetary actions and fulfilment serialize on the order row. Repeated handover is idempotent. Storage stays separate from product balance and CRM payment fields.
- No ID numbers, copies or collector phone are requested. Staff visually inspect original photo ID. The approved collector-profile retention is the later of ready+14 days and collection/cancellation+14 days; active records are retained. The new owner-only bounded cleanup is prepared with a paused schedule; terminal cancellation representation, retention holds and separate audit/mailbox retention need the controls described in the replacement guide.
- Google Sheets `warehouse_v3` and CRM field mappings are unchanged. They do **not** back up storage payments, policy acceptance, or delegated authorisations. Supabase database backup/recovery needs to cover the new tables. If staff need storage status in Sheets, prepare a separate versioned minimal export/schema migration; never add pickup hashes or management URLs to a spreadsheet.

### Rollback

Before any v2 orders exist, disabling the flag and rebuilding returns to the old registration/UI while retaining the additive schema. After v2 orders or fees exist, disabling the flag alone is **not** a complete rollback: the SQL handover/notice safeguards still apply, clocks and accepted obligations remain, and the old UI cannot manage them. First pause affected accepted orders with audited reasons, preserve ledger/customer records, then agree a compatible rollback or forward fix. Do not drop the new tables/triggers or erase accepted terms/payments to make a handover succeed.

## Acceptance test plan

- New order: unchecked/missing/forged policy consent rejected at both app and SQL; checked consent saves version/time. Existing orders and delivery orders never accrue these fees.
- Order → deposit → balance email: correct image/product/batch/quantity/amount, image-blocked fallback, support address and replies. Private links remain private and original bank verification remains authoritative.
- Mark ready with queued/failed/review email: no fee clock. Provider acceptance: notice timestamp set once. Exact 7/14/21-day boundaries, many weeks with no cap, pause/resume, extension, reduction and subsequent accrual are correct.
- Admin reason required; exact bank amount/reference required; bank reference reused across product/storage ledgers rejected in both directions. Later reductions/extensions after a storage payment are visibly retained and manually reconciled.
- Owner pickup: product/balance still fully paid, due storage settled/adjusted, current customer identity checked. Delegated pickup: consent/name/phone, bad/expired/revoked/replaced code, expired/revoked management URL, changed email/readiness, and wrong order all fail closed. Two simultaneous handovers produce one fulfilment/audit entry.
- Public/anon/authenticated RPC calls and direct-table reads denied. Unauthorised admin mutation denied before DB access; tampered tokens do not cause DB calls; throttling/RPC failures return safe errors. No raw code, private URL or secret appears in logs/audits/CRM/Sheets.
- Review/cancel: 21-day review does not silently forfeit/refund/dispose. Refund stops future fees. Owner communications and any final financial/cancellation decision remain explicit.
- Phone/mobile and desktop visual QA: checkout wrapping, checkbox readability, support links, balance image rendering, private form, admin fee totals and handover mode. Database concurrency tests locally use PGlite's serialized connection; verify true separate-connection contention in staging, not just local Promise.all.
